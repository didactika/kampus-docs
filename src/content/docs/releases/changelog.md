All notable changes to Kampus are recorded here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Versions, support branches and upgrades follow DEC-081 and DEC-082; the **Upgrade** group lists every action an operator must take.

## [Unreleased]

### Changed

- Themes follow the colour system of Material 3 with Didactika's identity as the default. A scope sets **seed colours** (`brand`, `primary`, `secondary`, `accent`, `neutral`, `danger`, `success`, `warning`, `info`), the typefaces (`font_family`, `font_family_brand`), `font_size`, `radius` (the medium corner, 0 to 28), `density` (`comfortable` or `compact`), `motion` and `scheme` (`system`, `light` or `dark`). Each colour grows a tonal palette (Didactika's own palettes as they are, any other seed in OKLCH keeping its hue), and the theme gives the colour roles of a light and a dark scheme (`primary`, `on-primary`, `primary-container`, `on-primary-container`, surfaces, outlines and inverse roles). A role keeps its seed when it is accessible and the nearest accessible tone otherwise, so every text keeps WCAG 2.2 AA contrast whatever the seeds. `GET /api/v1/customise/scopes/{scope}/theme` also returns the `light` and `dark` roles, and `theme.css` writes the custom properties of the design system of the client (`--k-color-<role>`, `--k-font-family-plain`, `--k-radius`, `--k-density`…) for both schemes, so the theme of a scope replaces the whole look without code. The tokens `on_*`, `surface`, `background`, `link` and `spacing` are gone; tokens a scope set before that no longer exist are ignored.
- The development PostgreSQL syncs its data directory with `syncfs` when it starts after a crash, so it is ready in seconds however many files the test database left behind.
- The buckets of the development store are created only when missing, so starting the compose file again no longer fails.
- The web client is a Next.js application in React and TypeScript (DEC-089), with the look of Didactika's theme: Inter, the gradient of the brand on the main action and the bar, tinted shadows. The home is a page of widgets the campus arranges (welcome, catalogue, latest notifications, text), which whoever may arrange it edits in place; the catalogue of courses has its own page (`/courses`) with search, filters, order, cards or a list and the pager; the main navigation is the menu the campus set; the sign-in page shows the brand of the campus beside the form. Pages are rendered on the server with the theme of the campus of the person, and the scheme the person chose applies before the first paint. The sign-in page, the courses of the campus, a course (its sections with the state of each activity, the grades of the person and the next 30 days) and the notifications are there, in English and Spanish chosen from the request, on light, dark and narrow screens. The browser reaches the API through `/api` of the same origin, forwarded to `KAMPUS_API_URL` (server role of the `web` image, default `http://localhost:8100`), and the image runs the standalone server of Next.js on port 3000. How every screen looks and behaves is written in the Kampus design system (`docs/03-design/web/design-system.md`).
- A password never holds spaces or other blank characters: setting one with a space is rejected with the rule `whitespace` (`identity.password_rejected`). Passwords already set are not affected. The development administrator of `compose.yaml` has a password without spaces; change the one of an existing development database from the account page before pulling, or recreate it.
- The web client has every step of the access: a second factor at sign-in (authenticator app, code by email or recovery code), recovering the access by email, activating an account from an invitation or a sign-up, and confirming a new email. A new password is checked as it is typed (no spaces, both copies equal) and each rule the campus rejects is explained under the field. Changing the password raises the session with the current password when the sign-in is too old, and then asks to sign in again, since every session ends. The links of these emails carry their token in the fragment (`/recovery/complete#token=…`).
- Two-step verification in the security of the account: the second factors of the person with their kind, name and last use, each of which can be removed; adding an authenticator app (a QR code and a key to type, confirmed with a code the app shows) or codes by email; and a new set of recovery codes, shown once to copy or download. A change that needs a recent sign-in asks for the password in a dialog and goes on. The QR code is drawn in the browser (`qrcode` 1.5.4), so the secret never leaves the page.
- Deployment: `deploy/compose` installs Kampus on one server with PostgreSQL, Valkey, the web client and Caddy for HTTPS, from `.env` (`.env.example`); a one-off `setup` service runs `install` and `upgrade` at every start. `deploy/helm/kampus` is a Helm chart with one Deployment per role, the web client, an Ingress and a setup Job per revision that the pods wait for (`kampus-server check`); it reads its secrets from a Secret of your own. `kampus-server secret-key` prints a new secret key. The operator guide covers both, backups and monitoring.
- Metrics in the Prometheus format at `/metrics` on every role: requests by method, route template and status with their duration, jobs by type and outcome with their duration, the connections of the pool and the version of the build.
- `server.trusted_proxies` (`KAMPUS_SERVER_TRUSTED_PROXIES`): the proxies whose `X-Forwarded-For` tells the address of people, read from the right; none by default. Before, the address of every request behind the web client was the web client's, so fifty failed sign-ins locked everyone out and sessions recorded the proxy. Deployments behind a proxy must set it; the Compose and Helm deployments do.
- A service no longer holds a database connection while it calls another service: under load, every connection ended up waiting for a second one and requests failed after 30 seconds. Checks and reads take the held connection (`Access::require_in`, `check_in`, `require_while_frozen_in`, `second_factor_required_in`, `Courses::course_in`, `section_in`, `Policies::policy_in`, `Participants::any_in`, `Records::graded_accounts_in`, `Settings::resolve_prefix_in`), `tools/repo-check` refuses the pattern, and a server test serves the pages of the client with a pool of one connection.
- Answers of the API carry `Cache-Control: no-store` unless they set their own caching. Pages of the web client carry a content security policy with a nonce per request and `Strict-Transport-Security`.
- A configuration variable set to an empty value counts as unset.
- Load test (`tools/load/campus.js`, k6) and the security review of 0.1.0 (`docs/05-quality/security-review.md`).
- `kampus-server reference` prints what every module of the build declares (permissions with the role templates that grant them, settings, features, terms, events, notification types, jobs and their schedules) as JSON, without a configuration or a database. Its snapshot `docs/03-design/reference.json` is what the handbook generates its reference pages from; a server test fails when a module changes its declarations without it (`KAMPUS_UPDATE_REFERENCE=1` rewrites it).
- The bar of the web client has the help of each screen: an icon that opens the guide of the handbook for that page, in the language of the reader, when `KAMPUS_HELP_URL` (server role of the `web` image) sets the address of the handbook.
- End-to-end tests of the web client in a real browser (Playwright 1.65): signing in, refusing a wrong password, the home and its editor, the search of the catalogue, a course, the notifications and the account, and a WCAG 2.2 AA check with axe of every page in the light and the dark scheme (`npm run e2e -w @kampus/web`).
- The web client is an npm workspace at the root of the repository: the shell in `web/`, the design system in `web/ui/`, the API client in `web/sdk/` and the UI module of each Kampus module in `crates/<module>/web/`. CI checks, tests and builds it (job *Web client*); its image builds from the root (`web/Dockerfile`).
- The development and CI store is SeaweedFS 4.54 with an identity, so it checks signatures and applies the type, disposition and cache control a signed link asks for; tests of store-signed links check what the store answers and that changed or unsigned links are refused. Run `docker compose up -d s3 s3-buckets` once to recreate the local store.
- The connection pool of each process closes connections idle for 2 minutes or open for 30 minutes, and waits up to 30 seconds for a connection instead of 10, retrying while PostgreSQL has no free slot. The development PostgreSQL accepts 300 connections and the tests of the `rust` service go through PgBouncer in `session` mode (`pgbouncer` in compose), which caps the server connections and makes other clients wait; the `rust` service runs 16 tests at a time and every integration test closes its pool, so several test runs at once no longer run out of connections. A pooler in front of PostgreSQL must keep sessions (PgBouncer in `session` mode), since upgrades hold a session lock. Run `docker compose up -d postgres pgbouncer` once to apply it.
- The examples and tests of external references use `lms` as the other system.
- The HTTP API of every module lives under the name of its module: `/api/v1/<module>/…` (for example `/api/v1/identity/auth/sign-in`, `/api/v1/users/me/profile`, `/api/v1/courses/courses/{id}`, `/api/v1/enrol/courses/{id}/participants`, `/api/v1/customise/scopes/{scope}/terms/{code}`). The server mounts each module under its name, so routes of two modules never collide, whatever either adds later. The package routes of customisation are now `/api/v1/customise/scopes/{scope}/packages`, `/api/v1/customise/scopes/{scope}/imports` and `/api/v1/customise/imports/{id}[/apply]`.
- The development PostgreSQL has 512 MB of shared memory, and every integration test drops the installation it creates, so the test database no longer grows run after run.
- Every component keeps its version data in its own `version.toml`, in the same form as the platform's; `kampus_common::manifest!()` reads it, and no version data is written in code.
- Tests live only in `tests/`, in one folder per kind (`unit`, `integration`, `conformance`, `support`), each one test binary with one file per topic; `tools/repo-check` rejects tests in `src/` and loose test files.
- Code no longer cites the specification: comments, documentation comments and test names describe behaviour in plain words, and `tools/repo-check` rejects identifiers of rules, requirements, use cases, decisions or tasks in code. The explanation of a permission check gives a reason (`allowed`, `no_allow`, `forbidden`, `guest_limit`, `frozen_scope`, `inactive_account`, `view_as_limit`, `unknown_permission`) instead of a rule identifier, and the schema linter reports SQL without a reason as `L-09`.
- Foundation, port, adapter and server crates follow the layout of DEC-087 too: only entry files at the top of `src/`, every concern in a folder with its `mod.rs` (for example `kampus-db`: `connection/`, `schema/`, `upgrade/`, `lint/`; `kampus-server`: `commands/`, `config/`, `http/`, `wiring/`), checked by `tools/repo-check`. Public paths are unchanged, except `kampus_server::run` (now `commands`) and the server's generated registries (now in `wiring/`).
- Every module crate follows one layout (DEC-087): `src/module.rs` exposes the `MODULE` descriptor, and the schema, permissions, model, services, ports, helpers and jobs each live in their folder. The server installs and synchronises modules only from their descriptors, listed in a registry `tools/repo-check --fix` writes from the module crates and from `crates/server/modules.toml`; CI rejects files outside the layout. Paths moved accordingly (for example `kampus_identity::service::sign_in`, `kampus_access::permissions`).
- Crate folders drop the project prefix (`crates/common`, `crates/db`, `crates/server`…), and adapters become sub-plugins of their port in `crates/<port>/adapters/<name>`, registered by URL scheme in a registry `tools/repo-check --fix` writes; external adapters are declared in `crates/server/adapters.toml` (DEC-086).
- The server opens the file storage and the cache from its configuration, through the adapters of the build, and its readiness checks both.
- Kampus is free software under the GNU Affero General Public License, version 3 or later (DEC-085), instead of a proprietary licence.

### Fixed

- A role granted or an enrolment made "now" is valid at once even when the wall clock of the host steps back (a virtual machine resyncing with its host, an NTP correction): the system clock never answers an earlier instant than one it already gave in the process, and active participation and `Access::holds_role` compare with that clock instead of the database one, so the start and the check come from the same clock. `Participation::new` takes the clock.

### Upgrade

- `KAMPUS_STORAGE_PUBLIC_URL` (optional, server and worker roles, `http://` or `https://`) is the address browsers reach the S3 store at; with it, files that cannot run are read from the store directly, and without it every file is served by the API, as before. The store must answer browsers at that address, with the same bucket and credentials. `Storage::presign_read` takes the `ReadHeaders` of the response, and an adapter signs only when it knows the public address.
- The first start, or `kampus-server upgrade`, installs the `activities` schema (steps 1 to 4). `Module` gains `condition_kinds`. `Module` gains `activity_types` (empty when a module has none). `files` accepts the area type `*/*` for areas that take any content.
- The first start, or `kampus-server upgrade`, installs the `records` schema (steps 1 to 6). The task runner gains the job `records.recalculate`, which runs when something is queued and every minute.
- The first start, or `kampus-server upgrade`, installs the `progress` schema (steps 1 to 5). `Module` gains `progress_rules`. The task runner gains the job `progress.recalculate`, which runs when something is queued and every five minutes.
- The first start, or `kampus-server upgrade`, installs the `calendar` schema (steps 1 to 3).
- The first start, or `kampus-server upgrade`, installs the `notify` schema (steps 1 to 4). `Module` gains `notification_types` (empty when a module declares none).
- The first start, or `kampus-server upgrade`, installs the `privacy` schema (steps 1 to 5). `PrivacyRun` gains `purge`. `PrivacyHandlerDeclaration` gains `erase`.
- The first start, or `kampus-server upgrade`, adds `files` step 3 (conversions). Links to files made before it stop working, since links now name what they read; they last five minutes anyway.
- `KAMPUS_SCAN_URL` (optional, server and worker roles) turns on malware scanning; without it uploads are kept unscanned, as before.
- `KAMPUS_MAIL_URL` (optional, worker role) sends email through an SMTP server, with `KAMPUS_MAIL_FROM` (required with it) and `KAMPUS_MAIL_USERNAME` and `KAMPUS_MAIL_PASSWORD` to sign in; without it the email channel writes to the log what it would send, as before.
- `KAMPUS_PUSH_URL` (optional, worker role) sends push notifications to browsers and phones, with `KAMPUS_PUSH_VAPID_PRIVATE_KEY` from `kampus-server push-key` and `KAMPUS_PUSH_SUBJECT`, both required with it; keep the key, since devices subscribe with it. Without it the push channel writes to the log what it would send, as before.
- The first start, or `kampus-server upgrade`, adds `files` step 2 (quotas); the usage of the files attached before it starts at zero.
- The first start, or `kampus-server upgrade`, installs the `files` schema and adds `users` step 3 (profile pictures). `Module` gains `file_areas` (empty when a module has none). Files need the storage port (`KAMPUS_STORAGE_URL`) in the roles that serve the API and run jobs; `kampus_identity::SecretKey::derive` gives each purpose a key of its own.
- The first start, or `kampus-server upgrade`, adds `users` step 2 and `enrol` step 2 (external references).
- The first start, or `kampus-server upgrade`, adds `courses` step 3 and `identity` step 3 (external references).
- Clients call every route under the name of its module (`/api/v1/<module>/…`); the routes without it no longer answer. The return address of OpenID Connect providers is now `<site>/api/v1/identity/auth/oidc/{provider}/callback`: register it again at each provider.
- The first start, or `kampus-server upgrade`, adds `customise` step 4 (imports of packages).
- The first start, or `kampus-server upgrade`, adds `customise` step 3 (rules and their runs). `Module` gains `rule_actions` (empty when a module has none). Enrolment events now carry the scope of their course.
- The first start, or `kampus-server upgrade`, adds `customise` step 2 (layouts, menus and themes). `Module` gains `page_kinds`, `widgets` and `menu_kinds` (empty when a module has none); `ValueKind::stored` and `ValueKind::stored_accepts` check values against a kind as stored.
- The first start, or `kampus-server upgrade`, installs the `customise` schema and adds `courses` step 2 (`course_field`). `Module` gains `terms`, `flags` and `field_kinds` (empty when a module has none).
- The `worker` and `all` roles now run the jobs of every module and need `KAMPUS_SECURITY_SECRET_KEY`; the `scheduler` and `all` roles fire the schedules. Run at least one of each.
- `kampus_module::http::HttpContext` is now `kampus_module::ServiceContext`, shared by routes and jobs; modules declare `settings`, `events`, `listeners`, `jobs` and `schedules` in their descriptor (empty when they have none), and `PreferenceKind` is now `ValueKind`, shared by preferences and settings.
- The identity policy that was fixed now comes from settings with the same defaults; nothing changes until an operator or an administrator sets a value.
- The `server` and `all` roles now need `KAMPUS_SITE_URL` and `KAMPUS_SECURITY_SECRET_KEY` to serve the API. Until a module delivers mail, the notices of identity (invitations, links, codes) are only logged as due, without their links.
- The configuration file is `config.toml` (was `kampus.toml`), with one table per section; variables follow `KAMPUS_<SECTION>_<KEY>`: `KAMPUS_PUBLIC_URL` is now `KAMPUS_SITE_URL`, `KAMPUS_ROLE` `KAMPUS_SERVER_ROLE`, `KAMPUS_HTTP_ADDRESS` `KAMPUS_SERVER_HTTP_ADDRESS` and `KAMPUS_UPGRADE_ON_START` `KAMPUS_SERVER_UPGRADE_ON_START`. `KAMPUS_SECURITY_SECRET_KEY` (32 bytes in base64) is required by the server and worker roles; `kampus-server install` generates it.
- The first start, or `kampus-server upgrade`, adds the registry of components (`db` step 2) and records every component of the build; from then on every upgrade, downgrade and uninstall is in `kampus-server history`.
- `KAMPUS_STORAGE_URL` is now required for the `server`, `worker` and `all` roles (`file:///path` or `s3://bucket/prefix` with `KAMPUS_STORAGE_S3_ENDPOINT`, `_REGION`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY`); `KAMPUS_CACHE_URL` turns on the shared cache.
- New configuration variables: `KAMPUS_HTTP_ADDRESS`, `KAMPUS_CONFIG_FILE`, `KAMPUS_UPGRADE_ON_START`, `KAMPUS_LOG_FORMAT`. A new installation is created by `kampus-server upgrade`, or at start with `KAMPUS_UPGRADE_ON_START=true`.

### Added

- The account of the person in the web client (`/account`): their profile (names, display name, language and time zone, saved against the version read) and its security (changing the password, and the open sessions, named by browser and system, each of which can be closed). The language of the profile chooses the language of the interface before the browser does. The bar shows an avatar with the initials of the person and a menu to the account, the notification preferences and signing out. Texts can have plural forms.

- Widgets for the page of a course (`courses.course`): `progress.course` (the progress of the reader), `records.grades` (their grades) and `calendar.upcoming` (the dates ahead, 7 to 90 days), beside `courses.outline`, `courses.summary` and `customise.text`.

- `@kampus/sdk` (`web/sdk`): the types of every route and schema of the API, produced by openapi-typescript from a snapshot of the document the server serves (`web/sdk/openapi.json`); a server test fails when the API changes and the snapshot does not. The web client reads the API through these types, which found that it read the type of course modules and notifications under the wrong name.

- The home of a site is a page kind of customisation, `customise.dashboard`, with the regions `top`, `main` and `side`, so each scope arranges it with widgets. New widgets for it: `customise.welcome` (a greeting with the figures of the reader), `courses.catalogue` (the courses of the campus to search, filter and open; heading, view and page size) and `notify.inbox` (the latest notifications); `customise.text` fits it too. Reading a layout says whether the reader may change it there (`editable`: they hold `customise.layout.manage` and no scope above locks it) and then lists the widgets they may place with their declared settings; reading a menu says whether it is editable.

- `@kampus/ui` (`web/ui`), the design system of the web client, in React on MUI with Didactika's look (DEC-089). `createKampusTheme` turns the tokens and colour roles of a scope into an MUI theme with CSS variables and both colour schemes, and `KampusThemeProvider` applies it. Its look covers buttons that are pills and narrow while pressed, a tonal variant, labels above fields, tonal alerts, and the corners, surfaces, scrim and tinted elevation of the theme. Didactika's components on top of MUI fix what each element means: `Button` (filled, tonal, elevated, outlined and text; primary, danger and success; busy), `ButtonGroup`, `TextField` and `SelectField` with the label above, `ConfirmDialog`, `StatusBadge`, the expressive `Loading` indicator and toasts (`ToastProvider`, `useToast`). Icons are Material Symbols by name (`Icon`), which a theme can override with images of its own. Its tests run in Chromium and check forms, the dialog, toasts, icons, the theme of a scope and WCAG 2.2 AA with axe in both schemes.
- Files read from the store: with `KAMPUS_STORAGE_PUBLIC_URL`, the address browsers reach an S3 store at, links to files and thumbnails that cannot run (raster images, PDF, audio, video, plain text) are pre-signed by the store at that address, answered with the media type, an inline disposition with the name of the file and private caching for the five minutes of the link, so their bytes no longer go through the API. Active content, stores on the local disk and stores without the setting keep the link the API serves, with `nosniff`, a sandboxing content security policy and an attachment for content that could run. The storage port gains `ReadHeaders`, and `presign_read` signs at the public address with those headers.
- `kampus-activities` (`crates/activities`): course modules, activities and materials placed in the sections of a course. Modules provide **types** (`activity_types` in the descriptor, with typed settings); a course module is added, updated (`If-Match`), moved to a section of its course (its scope moves with it), copied (with the file of a file material, sharing the content) and deleted to the recycle bin of its course for 30 days, from where it is restored to its place or removed for good by the daily job `activities.purge` (a failure stays in the bin with its reason). Each course module has an activity scope under its section; who sees it follows its section and its own visibility, and a file of a material is read by whoever sees it. Activities provides the types `activities.page` and `activities.file`, the file area `activities.material`, the permission `activities.module.manage` (administrators, managers, teachers and section leaders) and the events `activities.module_*`. Routes under `/api/v1/activities`, including external references of course modules (found, set and added or updated by reference).
- `kampus-records` (`crates/records`), first part: the grade records of a course in a tree of categories (the root of the course and its total are created with the first change; each category has a total of its own, and a category is deleted only when empty), manual records a teacher defines (`records.manage`) and the records an activity declares for each grade it gives (`Records::declare_activity_record`, once per course module and grade, keeping what a teacher set). Grades are written by idempotent upserts on the record and the person (`PUT …/records/{id}/grades`, up to 500 at a time, all or none): the same grade twice changes nothing, every change keeps an immutable entry with its source and actor, the counted grade applies the multiplier and offset inside the range of the record, a teacher overrides a grade (it wins over later activity grades until removed), and records and grades are locked and hidden until a date. Everything a person sees goes through one rule: their own shown grades, everyone's with `records.view_all`, hidden ones with `records.view_hidden`; the grader report paginates on the server. Permissions `records.view_own`, `view_all`, `view_hidden`, `grade`, `override`, `lock`, `hide`, `manage`, `export`; events `records.record_created|updated|deleted`, `records.grade_changed`, `records.overridden`, `records.locked`; routes under `/api/v1/records`. Grades are exact decimals (`rust_decimal`). Aggregation, scales, letters and formulas come next.
- Records, second part: totals. Every category has a total record and the course has its own; the job `records.recalculate` recomputes the totals of the people whose grades changed, from the deepest category up, and publishes `records.total_changed` for each that changed. A category aggregates by mean, weighted mean, simple weighted mean, natural (the grades are added and its total takes the range its children add up to), median, lowest, highest or mode; empty grades are left out or count as zero, extra credit adds without raising the maximum, and drop lowest and keep highest apply to the methods that define them, dropping the larger maximum first among equal grades. A total can be overridden like any grade, a grade can be left out of the totals (`PUT …/grades/{account}/excluded`), and a total that adds up a hidden record or grade is hidden from whoever may not see hidden content. Changing a record or a category queues everyone with grades in the course.
- Records, third part: scales and letters. A scale (a list of two to fifty items) and a letter set (bands of percentages that start at 0) are defined in a scope with `records.manage`, as a new version each time, and are available in that scope and below; the nearest definition wins (`GET|POST /api/v1/records/scopes/{scope}/scales|letters`, `GET /api/v1/records/courses/{course}/scales|letters`). A record can grade with a scale: its range is the items, its grades are the position of an item, and it keeps the version it was set up with. `Records::letter_for_course` turns a percentage into a letter for the screens that show grades.
- `kampus-progress` (`crates/progress`), first part: activity progress. A course module has rules (view, submit, grade, pass, or a manual mark by the learner); a person has the state `not_started`, `in_progress`, `done`, `done_passed` or `done_failed`, derived from the rules and what they did and re-evaluated on every view, submission, mark and grade (`records.grade_changed` and `records.overridden` are listened to). Every change of state is kept in a history and published as `progress.activity_changed`. A teacher decides a state with a reason (`progress.exception`) and it wins over the rules until removed; changing the rules queues the course module and the job `progress.recalculate` re-evaluates everyone who did something or has a grade, leaving decisions as they are. A person sees their own states and `progress.view_all` sees anyone's, and how a course module ended (passed or failed) is shown only when its grade is shown to the viewer. Permissions `progress.view_own`, `view_all`, `mark_own`, `exception`, `manage`; routes under `/api/v1/progress`. `Progress::notify_view` and `Progress::notify_submission` are for the modules that provide activities. Records gains `Records::activity_grade`, `module_of_record`, `graded_accounts` and `modules_with_visible_grade` for modules that react to grades. Criteria, course progress and prerequisites come next.
- `kampus-calendar` (`crates/calendar`), first part: entries of a campus, a category or a course (`calendar.manage`, seen with `calendar.view`) and personal entries nobody else sees, created, replaced on their version and deleted (`/api/v1/calendar/entries`), listed for a window of up to a year, and the calendar of a course (`GET /api/v1/calendar/courses/{id}/calendar`), which adds when each course module the person sees opens, is due, closes and stops accepting late work with the exceptions of that person applied. The dates of activities are read each time and never copied. Events `calendar.entry_created|updated|deleted`. `Activities::module_values` gives the dates a course module has of its own. Recurrence, subscriptions and feeds come next.
- `web/`: the first web client, an application shell in TypeScript built with Vite and served by nginx (`docker compose up -d web`, http://localhost:8101, which proxies `/api` to the server so the session cookie is same-origin). It has a router, a session, message bundles in English and Spanish with locale-aware dates and numbers, design tokens with a dark scheme, Web Components of the design system (`k-field`, `k-button`), a skip link, landmarks, visible focus, live regions and reduced-motion support, and an escaping template tag so data never becomes markup. Screens: sign in, courses by category, a course (sections and course modules with the progress of the caller, grades and the next 30 days of the calendar) and the notifications inbox. Parts of a course the caller may not see, or that the installation does not offer, are left out instead of failing the page.
- `kampus-notify` (`crates/notify`), first part: modules declare notification types (`Module.notification_types`: code, summary, default channels, required), listeners create notifications after the change commits, and each person reads an inbox (newest first, unread count, mark read one by one or all) and chooses which types they receive; a required type cannot be turned off, and a listener that runs twice for one event notifies once. Records declares `records.grade_posted`, announced only when the person may see the grade, and progress declares `progress.state_decided`. Event `notify.delivered`; routes under `/api/v1/notify`. Email and push channels, templates, conversations and messages come next.
- `kampus-privacy` (`crates/privacy`), first part: export of personal data. A person asks for an export of their own data, or someone with `privacy.request.manage` in their campus asks for another account's (`POST /api/v1/privacy/requests`); the request is split into one part per data category, each answered by the handler a module declares (`Module.privacy_handlers`, today records, progress, notify and calendar) in the job `privacy.run`, and the package (`GET …/requests/{id}/package`) is available only to the person who asked for 7 days, after which the job `privacy.expire` forgets the data. Events `privacy.request_created` and `privacy.request_completed` (audited). Deletion, retention, legal holds, policies and file packages come next. `Module` gains `privacy_handlers`.
- `kampus-privacy`, second part: policies. A campus publishes versions of its policies (`POST /api/v1/privacy/policies`, permission `privacy.policy.manage`, held by administrators), people read the latest ones (`GET …/policies`, `…/policies/pending`) and accept the version in force (`POST …/policies/{code}/acceptance`; an older version answers `privacy.policy_outdated`, accepting twice changes nothing). Events `privacy.policy_published` and `privacy.policy_accepted` (audited). What a person accepted is part of their export through the handler `privacy.acceptances`.
- `kampus-privacy`, third part: deletion. `POST /api/v1/privacy/requests` with `kind: deletion` and a reason asks for the erasure of personal data; it waits for someone with `privacy.request.approve` (`GET …/requests/awaiting`, `POST …/requests/{id}/decision`) unless whoever asks holds it. Once approved, each module erases its data through the `erase` of its handler (notify and calendar delete; records, progress and privacy keep what belongs to the academic record or to the proof of acceptance) and identity leaves the account as a tombstone with a pseudonym. Legal holds (`privacy.hold.manage`, `GET`/`POST …/holds`, `POST …/holds/{id}/release`) on an account or on a whole campus keep a deletion in `held` until released or ended. Events `privacy.request_decided`, `privacy.account_erased`, `privacy.hold_placed` and `privacy.hold_released` (audited).
- `kampus-privacy`, fourth part: retention. A campus sets how many days each kind of data that an erasure keeps stays after the account is deleted (`GET /api/v1/privacy/retention`, `PUT …/retention/{category}`, permission `privacy.retention.manage`); the daily job `privacy.retain` asks the handler to purge it (`purge` in the run) when the time ends, unless a legal hold covers the account, and records it so it never repeats. Records, progress and privacy purge grades, progress and acceptances. Event `privacy.data_purged` (audited).
- `kampus-privacy`, fifth part: the package of an export is a file. Once every part is answered, privacy puts the answers together as a JSON file of the area `privacy.package` (declared in `src/settings/files.rs`), owned by the person who asked and readable only by them while the request has not expired; the parts forget their data, and the file is deleted when the request expires. `kampus-files` gains `Files::store_for` (content a module made itself, with the same area checks, scan, storage by hash and quotas), `read_content` and `remove`.
- `GET /api/v1/openapi.json`: the OpenAPI 3.1 document of the API the installation serves, read from the routes the modules really mounted (paths, methods, path parameters, authentication, the `x-kampus` header and the problem document), so it never lists a route that does not exist.
- The OpenAPI document describes what every operation takes and answers: its summary, the JSON schema of its request body and of its success answer (or the media type of bytes, a redirect, or nothing on `202`/`204`), and the problem details (RFC 9457) every error answers with, as the shared schema `Problem`. Each module declares its operations next to its routes (`OPERATIONS` in `src/http/mod.rs`, exposed as `Module.operations`), and the schemas are derived from the Rust types of the bodies with `schemars`, so they follow the code. A test fails when a route has no operation, when an operation has no route or no documented answer, or when a schema does not resolve. Answers that were written as loose JSON are now typed (`kampus_module::http::Identified` for `{ "id": ... }`, the sign-in answer by its `status`, a created API token, the file of a picture or a material, among others), with the same fields as before.
- Notification channels: besides the inbox, email and push. What a person receives of a type on a channel follows one rule: a default of their campus that is locked, else their own choice, else the default of the campus, else the channels the type declares; a required type always reaches the inbox. Email and push are sent by the job `notify.deliver`, one delivery per notification and channel, tried again with a growing wait and given up after five attempts or when the person has no address; their text comes from the template of the campus in the language of the person (`{{summary}}` and the fields of the notification), or from the summary of the type. Administrators write templates (`notify.template.manage`, `…/campuses/{id}/templates`) and set defaults (`notify.defaults.manage`, `…/campuses/{id}/defaults`); people register their browsers and phones (`…/push-subscriptions`) and see their preferences per channel, with what the campus locked. The transports are a port of notify (`ports::transport::Transport`); until one is configured the server writes them to its log. `Identity::email_of` and `Users::language_of` read what a delivery needs.
- Personal calendar feeds and subscriptions to other calendars. A person makes a feed (`POST /api/v1/calendar/feeds`) and gets, once, a secret address (`GET /api/v1/calendar/feed/{secret}`) that a calendar application reads as iCalendar: what they see now in their courses and their own entries, from a month ago to almost a year ahead; only its hash is kept, and it can be revoked. Whoever manages the calendar of a scope subscribes it to the calendar of another system (`…/scopes/{id}/subscriptions`); the job `calendar.refresh` reads it every so often (and `…/subscriptions/{id}/refresh` now), only at public network addresses, without following redirects and up to 5 MB, matches its events by UID and applies what was added, changed or removed, and the scope shows them as `imported` items. Events `calendar.subscription_refreshed`, `calendar.feed_created` and `calendar.feed_revoked`.
- Calendar entries that repeat, last whole days, follow a time zone or are for a group: `recurrence` (an RFC 5545 rule: `FREQ` daily, weekly, monthly or yearly, `INTERVAL`, `COUNT` or `UNTIL`, `BYDAY` for weekly and `BYMONTHDAY` for monthly rules), `time_zone`, `all_day` (from midnight to midnight in that time zone) and `group` (a group of the course, seen by its members and whoever manages the calendar). A recurring entry is stored once and expanded in each window, keeping its time of day across daylight saving changes; one occurrence is cancelled or changed with `PUT /api/v1/calendar/entries/{id}/occurrences/{at}` and restored with `DELETE`. Items say whether they are `all_day` and, for an occurrence, when the rule started it.
- The setting `progress.notify` (campus, category or course; `progress.manage`, on by default) says whether the people of a course are told when they complete it or a teacher decides their progress; notify reads it before announcing.
- Rules of progress declared by activity types (`Module.progress_rules`: code, activity type, summary): a teacher requires them of a course module of that type (`GET`/`PUT /api/v1/progress/course-modules/{id}/type-rules`, which also lists what the type offers), the module of the type reports for each person whether they meet one with `Progress::report_type_rule`, and they count like the other rules. `Activities::type_of` reads the type of a course module.
- Prerequisites between courses (`PUT /api/v1/progress/courses/{id}/prerequisites`, `progress.manage`; `GET` answers what a course requires first and what requires it): a cycle is refused (`progress.prerequisites_cycle`), also through course criteria, and someone who enrols themselves is refused with `enrol.prerequisites_missing` while a course required first is not completed; a teacher who enrols someone is not stopped. Enrolment asks through a new port, `kampus_enrol::ports::gate::JoiningGate`, which progress implements (`PrerequisiteGate`). Event `progress.prerequisites_changed` (audited).
- Course progress (`PUT /api/v1/progress/courses/{id}/criteria`, `progress.manage`): a course requires typed criteria combined with `all` or `any` (a course module done or passed, a grade as a share of its range, a date, days taking part without a break, the approval of someone who holds a role in the course, another course completed), and may say a completion is final. The people it follows are its active participants who hold `progress.tracked` (learners). Listeners of activity progress, grades, totals and completions queue them, the job `progress.course_recalculate` evaluates them and `progress.course_timed` queues daily the courses whose criteria depend on time; a completion is recorded with its history and revoked when a criterion stops being met unless it is final. Reads: `…/course-progress` (everyone followed), `…/course-progress/{account}`, `…/my-course-progress`, each criterion with whether it is met; approvals with `PUT /api/v1/progress/criteria/{id}/approvals/{account}`. A course that would require itself is refused, and a criterion that stays the same keeps its approvals. Events `progress.course_completed`, `progress.course_revoked`, `progress.criteria_changed` and `progress.approved` (audited), and the notification `progress.course_completed`. `Access::holds_role`; the `Participants` port of courses gains `accounts` and `since` (`Courses::participants_of`, `Courses::taking_part_since`); `Records::course_of_record` and `Records::grade_share`.
- Formulas of grades (`PUT /api/v1/records/records/{id}/formula`, `records.manage`): a manual record or a total computes its grades from other records of the course, written `[[<record id>]]`, with `+ - * /`, parentheses and `min`, `max`, `sum`, `average`, `round`, `floor`, `ceil`, `abs`, exactly with decimals and within the range of the record. What a formula reads is kept as relations, a cycle (also through a total) or an unknown record is refused, a computed record takes no grades by hand (`records.record_derived`), and deleting a record a formula reads answers `records.record_used_by_formula`. The recalculation job computes formulas and totals in the order of what they read.
- Exports of grades (`POST /api/v1/records/courses/{id}/exports`, `records.export` and `records.view_all`): the job `records.export` writes a CSV of what the person who asked may see, with names (`Users::names_of`) and one column per record, quoted and never read as a formula by a spreadsheet, as a file of the area `records.export` only they read; `GET …/exports/{id}` follows it, and the daily job `records.export_expire` removes the file after a week.
- Grades survive the end of a participation: the grader report and exports leave out the people who no longer take part unless `include_inactive=true`, each row says whether the person is `active`, and nothing comes back wrong when they enrol again. `Courses::takes_part` reads the participation for modules.
- Access conditions of course modules and sections (`activities.conditions.manage`, and `activities.conditions.ignore` to open everything, both held by the same roles as `activities.module.manage`): a tree of `all`, `any` and `not` over leaves of kinds that modules declare (`Module.condition_kinds`), each kept in the table of its module: `activities.date` (from, until or between), `activities.group` (a group, a group of a set, or any group), `activities.profile` (a field of the profile compared to a value), `progress.state` (another course module done, not done, passed or failed) and `records.grade` (a share of the range of a grade record). `GET`/`PUT /api/v1/activities/course-modules/{id}/conditions` and `…/sections/{id}/conditions`; a tree on a section applies to everything inside it. Listings and reads answer `available` per course module: what a person does not meet is listed without its content, or left out when the tree says so, and its file is refused. Deleting a course module that conditions depend on answers `activities.module_required_by_conditions` unless `?remove_conditions=true`; a leaf of an unknown kind, or one that lost what it depends on, never holds. Event `activities.conditions_changed` (audited). `Courses::group_set` reads a set with its groups.
- Exceptions of course modules (`activities.exception.manage`, held by the same roles as `activities.module.manage`): for a type that declares the feature `exceptions`, a person or a group of the course gets their own opening and closing dates, due and cut-off dates, time limit and attempts, one exception each per course module (`PUT …/course-modules/{id}/exceptions/accounts/{account}` and `…/groups/{group}`, `GET …/exceptions`, `DELETE …/exceptions/{id}`). What applies to a person is resolved in one place, `Activities::effective_values` (`GET …/effective-values/{account}`; a person reads their own): their own exception wins setting by setting, otherwise the most generous of their groups, otherwise the settings of the course module. Event `activities.exception_changed`. `Courses::groups_of` lists the groups a person belongs to in a course.
- Conversions of files: `GET /api/v1/files/files/{id}/conversions/thumbnail` queues a job (`files.convert`) the first time and then answers with a 5-minute link to a PNG thumbnail of at most 256 pixels a side (PNG, JPEG, GIF and WebP images), decoded within limits; conversions belong to the content and are shared by every file with it, and `files.converted` is published when one is done. Links bind what they read, the original or a conversion.
- `kampus-server copy-storage <url>` copies every stored file to another store, verifying each by its hash, so the operator can switch `KAMPUS_STORAGE_URL` without stopping Kampus.
- Malware scanning: the scanning port `kampus-scan` (`Scanner`, `Verdict`, conformance suite with the EICAR test file) and its first adapter `kampus-scan-clamd` (`clamd://host:port`, ClamAV's `INSTREAM` over TCP). With `KAMPUS_SCAN_URL`, files scans every upload before keeping it and refuses infected content with `files.infected`; readiness checks the scanner. Compose offers ClamAV under the `scan` profile.
- Mail: the mail port `kampus-mail` (`Mail`, `Mailer`, conformance suite) and its first adapter `kampus-mail-smtp` (`smtp://` in the clear or with `?tls=required` for STARTTLS, `smtps://` over TLS). A message takes up to 50 plain addresses and a subject on one line, so no address or subject can add a header (`mail.invalid`); a message the server refuses for good fails with `mail.rejected` and its delivery is not tried again. With `KAMPUS_MAIL_URL`, the email channel of notify sends through it (`MailTransport`). Compose runs Mailpit, whose inbox is at port 58025, and the suite runs against it in CI.
- Push: the push port `kampus-push` (`Device`, `Pusher`, `Outcome`, conformance suite against a push service that decrypts) and its first adapter `kampus-push-webpush` (`webpush://`: encryption for each device, RFC 8291, and a VAPID signature, RFC 8292). Endpoints come from browsers, so only public network addresses are reached, without following redirects. With `KAMPUS_PUSH_URL`, the push channel of notify sends the title and the text to every device of the person, forgets the devices their push service says are gone, and serves the public key at `GET /api/v1/notify/push-key` (`notify.push_unavailable` without push). `kampus-server push-key` generates a key.
- Conversations: a direct conversation exists once per pair of people, whoever opens it; a group conversation gathers up to 50 people its creator may write to; the conversation of a group of a course follows the members of the group. Who may write to whom is the campus setting `notify.messaging` (`course`, people who take part in a course together, by default; `campus`; `nobody`), which `notify.message.anyone` overrides (administrators), and a block stops writing either way without saying who blocked whom. Messages are sanitised rich text (`kampus_common::text`, the one rich-text format of user content), notify the other members who did not mute the conversation with `notify.message_received` (inbox and push), are deleted per person, and the nightly job `notify.message_purge` purges those every member deleted and those older than `notify.message_retention_days`. Routes under `/api/v1/notify/conversations`, `/messages/{id}` and `/blocks`. Courses tell who shares a course (`Courses::share_a_course`, a new operation of the `Participants` port) and the members of a group (`Courses::group_members_of`). Erasing a person also removes their devices, messages, memberships and blocks.
- Files of messages: a message carries up to 10 files the author uploaded to the area `notify.message` (10 MB each; images, PDF, text, office documents, zip), with `notify.message.attach`, which every signed-in person holds; a message may be only files. The members of the conversation read them, and they are detached with their message when it is purged or its author erased.
- Quotas of files (`files.quota.manage`): a limit in bytes for a scope, counting the attached files of the scopes inside it, and for a person, counting the attached files they uploaded (`GET`, `PUT /api/v1/files/scopes/{scope}/quota` and `/api/v1/files/people/{id}/quota`). An upload that would not fit is refused when it is opened, and an attachment that no longer fits is refused in its own transaction (`files.quota_exceeded`); what files take is counted as they are attached and detached. `Access::principal_campus` gives the campus of a principal.
- `kampus-files` (`crates/files`): content stored once by its SHA-256 in the storage port, with the count of the files that use it kept in the same transaction; areas modules declare (`file_areas`: limits, accepted types, upload permission, and who reads); one upload pipeline (`POST /api/v1/files/uploads`, `PUT` the raw content, `POST` to complete) that reads the media type from the content; files attached and detached by their owning module in its own transaction (`Files::attach_in`, `Files::detach_in`), readable exactly when their owner is and only by their uploader until then; links of 5 minutes (`POST /api/v1/files/files/{id}/url`, served by the API) serving the content with `nosniff`, a sandboxing content security policy and as an attachment when it could run; and an hourly purge of expired uploads, files nobody attached and content 7 days in the trash. Users keep a profile picture (`PUT`, `DELETE /api/v1/users/me/picture`, `GET /api/v1/users/accounts/{id}/picture`).
- External references of system groups (`/api/v1/users/system-groups/{id}/references[/{system}]`, found by `…/campuses/{campus}/system-groups/by-reference/…`, created once by `PUT …/scopes/{scope}/system-groups/by-reference/…`) and of enrolments (`/api/v1/enrol/enrolments/{id}/references[/{system}]`, found by `…/campuses/{campus}/enrolments/by-reference/…`, and `PUT …/enrolment-instances/{id}/enrolments/by-reference/…` enrols through a manual instance or changes the period; an identifier never names the enrolment of someone else).
- External references (the `idnumber` of other systems): (system, identifier) per record, unique per campus, system and kind of record, in tables of the module that owns the record (`kampus_db::reference_table!`, `kampus_db::references::References`), never in a column of the record. Categories, courses, sections, groups and group sets (`/api/v1/courses/{kind}/{id}/references[/{system}]`, `/api/v1/courses/campuses/{campus}/{kind}/by-reference/{system}/{external_id}`) and accounts (`/api/v1/identity/accounts/{id}/references[/{system}]`, `/api/v1/identity/campuses/{campus}/accounts/by-reference/…`) carry them; categories and courses are created or updated by them (`PUT …/categories/by-reference/…`, `PUT …/courses/by-reference/…`), with the reference set in the same transaction.
- Customisation packages in `kampus-customise` (`customise.package.manage`): `POST /api/v1/customise/scopes/{scope}/packages` exports what a scope itself sets of the kinds chosen (terms, flags, fields without values, layouts, menus, theme, rules) with its SHA-256; `POST /api/v1/customise/scopes/{scope}/imports` validates a package against the declarations, locks and permissions of the scope and keeps it with its differences, and `POST /api/v1/customise/imports/{id}/apply` checks it again and applies it once, in one transaction recorded as one change. Imports add and change, never remove; fields are matched by kind and code, rules by name.
- Rules in `kampus-customise`: a scope writes rules (`customise.rule.manage`) that react to an event type of any module in the scope and below, with typed conditions on the fields the event declares (`all`, `any`, `not`, `compare` with `eq`, `ne`, `in`, `exists`), and run actions modules declare in `rule_actions` with typed parameters, as the rule's owner, who must hold the permission each action declares. Each event is evaluated once per rule and recorded (`running`, `succeeded`, `failed`, `skipped`) with the actions done; a failure publishes `customise.rule_failed`. A rule cannot be triggered by events its actions publish, and no rule runs more than five events down a chain. Routes under `/api/v1/customise/scopes/{scope}/rules` and `/api/v1/customise/rules/{id}` (with `If-Match`) and its `/runs`. Courses offer `courses.add_to_group`, which adds the account of the event to a group. `kampus-events` declares `events.any`, whose listeners receive every event.
- Layouts, menus and themes in `kampus-customise`. Modules declare `page_kinds` (with their regions), `widgets` (with the page kinds they fit and typed settings) and `menu_kinds`. A scope arranges the widgets of a page kind (`customise.layout.manage`, held by teachers in their courses), sets the items of a menu (`customise.menu.manage`: labels, paths or web addresses, permissions, three levels) and the design tokens of its theme (`customise.theme.manage`), each resolved through the scope tree with locks and its origin; readers see only the widgets and items their permissions allow, and a widget no module declares any more is skipped. Themes keep every text colour at WCAG 2.2 AA contrast on its background, or are refused, and reach the client as CSS custom properties at `GET /api/v1/customise/scopes/{scope}/theme.css`. Customisation declares the `customise.main` and `customise.footer` menus and the `customise.text` widget; courses declare the `courses.course` page with the `courses.outline` and `courses.summary` widgets.
- `kampus-customise` (`crates/customise`): what a campus changes without code, kept per scope and resolved from the nearest scope up to the platform, sections included, unless a scope above locks it, with where it came from. Modules declare `terms` (singular and plural per language), `flags` (features with a default) and `field_kinds` (entities that accept custom fields) in their descriptor (`src/settings/customise.rs`). A scope renames terms per language, turns features on or off, and defines typed custom fields (text, integer, date, boolean, choice, choices, account; public or private); every change is recorded with before and after and publishes `customise.changed` (audited). Routes under `/api/v1/customise/scopes/{scope}/terms`, `/flags` and `/fields`, and `/api/v1/customise/fields/{id}`; permissions `customise.term.manage`, `customise.flag.manage`, `customise.field.manage`, `customise.field.view` and `customise.field.edit`.
- Courses declare the terms `courses.category`, `courses.course` and `courses.section` (English and Spanish), the feature `courses.groups` (creating a group where it is off answers `customise.feature_off`) and custom fields on courses, read and set with `GET /api/v1/courses/courses/{id}/fields` and `PUT /api/v1/courses/courses/{id}/fields/{code}`.
- `kampus-settings` (`crates/settings`): modules declare typed settings (`settings` in the descriptor, `src/settings/mod.rs`) with a default, the kinds of scope where each may be set and the permission that sets it; values are kept per scope and resolved from the nearest scope that sets them, unless a scope above locks them, with where the value came from; every change keeps who made it with the value before and after, and publishes `settings.changed` (audited). `kampus-server settings` lists, reads, sets, unsets and shows the history of settings.
- The identity policy of a campus is now made of settings (`identity.self_sign_up`, `identity.password_min_length`, `identity.session_idle_hours` and the others), set for the platform or a campus with the new permission `identity.policy.manage`; `courses.group_mode` is a setting of a course, a section or an activity.
- `kampus-events` (`crates/events`): declared event types with the fields of their payload, published with an outbox entry in the transaction of the change, dispatched after commit into one delivery per listener, delivered at least once and in order per object, retried with a doubling wait and dead after eight attempts, replayable; listeners can be turned off without losing deliveries; chains of events stop after ten; audited types write an append-only audit entry in the same transaction. Modules declare `events` (`src/events/`) and `listeners` (`src/observers/`); the `worker` and `all` roles run the deliveries; `kampus-server events` lists deliveries, replays dead ones, turns listeners on or off and shows the audit log; `events.purge` keeps events 90 days and audit entries two years.
- The first events: `users.system_group_members_changed`, `enrol.enrolment_created`, `enrol.enrolment_updated`, `enrol.enrolment_removed` (audited), `courses.course_created`, `courses.course_state_changed` (audited) and `courses.course_deleted` (audited). Enrolment listens to the members of system groups and brings the instances that follow a group in step at once.
- `kampus-tasks` (`crates/tasks`): a durable job queue on the database. Jobs are enqueued in the transaction that needs them, claimed with `FOR UPDATE SKIP LOCKED` under a lease as long as their timeout, retried with doubling back-off and failed visibly with their error; jobs sharing a concurrency key run one at a time; a job whose worker stops is taken again; long jobs report progress and stop when cancelled. Schedules fire on cron rules read in a time zone, once per instant across every node. Modules declare `jobs` and `schedules` in their descriptor (`src/jobs/`); the `worker` and `all` roles run jobs and the `scheduler` and `all` roles fire schedules. `kampus-server tasks` lists jobs and schedules, retries, cancels, changes a rule and runs a schedule now.
- Scheduled jobs: `identity.purge` (daily) and `identity.run_deletions` (hourly), `enrol.sync` (every 15 minutes) and `enrol.run_expiry` (hourly), `courses.run_deletions` (hourly; a course whose deletion is due goes with everything it owns) and `tasks.purge` (daily).
- `kampus-enrol` (`crates/enrol`): method instances of a course (manual, self, system group) with the role they give, an opening period, capacity, approval and expiry rule; enrolments that own the grant of their role for their period, checked against capacity and period with the instance locked; self-enrolment with keys hashed like passwords, one per course or per group, five wrong keys an hour at most, and requests that wait for a decision; system group instances kept in step with their group; the expiry rule applied once to each ended enrolment. Active participation is computed with the database clock and answers courses through its participants port, so only participants join groups and a course with participants does not go back to draft. Commands `kampus-server enrol sync` and `kampus-server enrol run-expiry`; routes under `/api/v1`.
- `kampus-access`: `grant_for_module_between_in` (a module's grant over a period), `revoke_for_module_in` and `require_may_grant`; `kampus-users`: `member_accounts`.
- `kampus-courses` (`crates/courses`): a tree of categories per campus, courses created as drafts with their first section and owned and taught by their creator, the course lifecycle (published, archived with its scope frozen, deletion scheduled after a grace period and cancelled back to draft), sections nested to any depth, moved with their subtree and deleted recoverably, groups limited to a section or not with manual and module-owned memberships, and group sets. Order among siblings uses fractional sort keys, so a move rewrites only the node that moves; visibility is each node's own and what learners see is computed from the node and its ancestors. Routes under `/api/v1` for categories, courses, sections, groups and group sets, with `If-Match` on every change.
- `kampus-access`: `move_scope_in` (a scope moves with its subtree, grants and overrides), `delete_scope_in`, `set_frozen_in`, `require_while_frozen`, `platform` and `campuses`. A permission declared for the first time, such as one of a module installed on a running site, now reaches the roles that already exist with the value of their template; values an administrator changed stay.
- The HTTP API of identity and users under `/api/v1`: sign-up, confirmation, invitations, sign-in with the second factor, step-up, sign-out, recovery, email change and providers (OIDC start and callback); the account signed in, its password, email, sessions, API tokens, second factors and recovery codes; invitations, service accounts, account transitions and other accounts' tokens for managers; profiles with `ETag` and a required `If-Match`, preferences and system groups. Browsers use the HttpOnly `kampus_session` cookie and send `X-Kampus` with every change; integrations send an API token as `Bearer`, limited to the permissions it carries. Errors are problem details with the request id.
- Modules declare their routes in `src/http/` through `routes` in the descriptor; the server builds the services once, finds the campus of each request and authenticates it before any route (`kampus_module::http`: `HttpContext`, `ApiResult`, `Body`, `id`, `if_match`, `with_etag`).
- `kampus-users` (`crates/users`): profiles (names, language, time zone) saved with `If-Match`, one's own or anyone's with its permission; preferences that modules declare with a type and a default (`preferences` in the descriptor); system groups of a campus or a category whose members are added by hand, by a rule over profiles or by a sync, a rule or a sync removing only what it added.
- Changing the email of an account in `kampus-identity`: step-up, a link to the new address, a notice to the current one, the username following the email when they were equal (`identity` step 2).
- Commands of components: a module declares them in `src/commands/` and the server runs them as `kampus-server <component> <command>`, with `kampus-server <component> --help`; identity offers `purge` and `run-deletions`.
- `kampus-server install`: writes `config.toml`, asking only for what the file and the environment do not give (or nothing with `--non-interactive`), generates the secret key, and creates the installation with its first campus and administrator; an installed database is left as it is. `config.example.toml` shows every section; the image reads `/etc/kampus/config.toml`.
- Multi-tenancy is configured in `[tenancy]` (`single`, or `multi` with a base domain).
- `version.toml` at the root describes the platform release (name, version, maturity, date, `upgrade_from`); the core reads it when it is built, registers the platform as the component `kampus`, and refuses installations older than `upgrade_from`.
- Components with versions (DEC-088): every module, plugin and adapter has a manifest (`kampus_common::manifest!`) built from its `Cargo.toml` and `assets/icon.svg`, with optional maturity, supported Kampus releases and requirements; names follow packages and folders (`kampus-cache-redis` is `cache_redis` in `crates/cache/adapters/redis`); the server checks them all before it installs, upgrades or starts.
- The registry of an installation: the installed version of every component and the ordered history of runs, failed ones included; new versions need an upgrade, and newer or missing components stop the start.
- Data actions in upgrade steps, run once in the step's transaction, and the way back: steps may say how to undo themselves, the SQL is kept when they are applied, and `kampus-server downgrade --yes` undoes newer steps or names the ones it cannot.
- `kampus-server components`, `history`, `downgrade` and `uninstall`; the command line moved to `kampus_server::commands::cli`.
- `kampus-macros`, and Lucide icons for the components of the repository (`THIRD_PARTY.md`).
- `kampus-module` (`crates/module`): the module contract, with the `Module` descriptor and the vocabulary of declarations (scope kinds, values, risks, permissions, role templates).
- Every crate states its kind (`foundation`, `port`, `adapter`, `module`, `server`) in `[package.metadata.kampus]`.
- OpenID Connect providers in `kampus-identity` (RN-028): authorization code flow with PKCE and nonce, the state sealed in the client instead of stored, ID tokens verified against the provider keys; identities link by issuer and subject, by a verified email only when the campus allows it, or after the owner confirms; the sign-in then runs the same pipeline as a password, second factor included.
- Docker Compose and CI start an OpenID provider for the tests (`ghcr.io/navikt/mock-oauth2-server`, localhost:58080).
- Second factors in `kampus-identity`: codes from authenticator apps (RFC 6238, secrets sealed with XChaCha20-Poly1305), codes by email and recovery codes shown once; a sign-in that needs one completes with it, or sets up the first app when the campus or a role requires it; a code is never accepted twice. Access recovery checks the second factor before the new password, is rate-limited, ends every session and token, and never signs in by itself (RN-029, RN-030).
- Roles can require a second factor from the people who hold them (`access` step 2).
- `kampus-identity` (`crates/identity`): accounts of a campus, unique by username and email without regard to case, each the principal of access with its own user scope; sign-up with an email link that never reveals whether an account exists; invitations; the account lifecycle with its history, `If-Match` and one permission per transition; deletion after a grace period that leaves a tombstone; Argon2id passwords checked against the campus policy; hashed, expiring one-time tokens; one sign-in pipeline with throttling per account, per name and per address; server-side sessions revoked at once on suspension or password change, with step-up for sensitive operations; scoped, expiring API tokens; and service accounts that use only tokens. One test per business rule (RN-022 to RN-027, RN-031 to RN-035, RN-039).
- The `unauthenticated` error kind (HTTP 401), for missing or wrong credentials and expired sessions.
- `kampus-access` (`crates/access`): the scope tree with nested sections and its closure table, principals, roles made from versioned templates with their allowances, manual and module-owned grants, overrides, permission checks that explain themselves, "view as", the history of every change, and the default roles of a campus; one test per business rule (RN-001 to RN-021). The server synchronises the declared permissions and templates at start-up.
- The neutral schema of `kampus-db`: modules declare tables, portable types, keys, foreign keys, checks and indexes, and the port writes quoted, prefixed PostgreSQL and indexes every foreign key; upgrade steps are lists of these changes, and SQL outside it needs a reason.
- The schema linter (`kampus_db::lint`), run on every build over every module, and the conformance suite of the database port: every type, reference behaviour, check, error class and `SKIP LOCKED`.
- `kampus_db::classify`, which maps database failures to the error model, and the capabilities of the database port.
- `kampus-storage`: the file storage port (keys, hash-verified writes, ranges, copies, presigned reads as a capability) with its conformance suite, and `kampus-storage-opendal`, which stores on the local disk or in any S3-compatible bucket.
- `kampus-cache`: the cache port (entries with a time to live, counters with a window, locks with a lease) with its conformance suite and the two-level `Layered` cache, and its adapters `kampus-cache-moka` (in-process) and `kampus-cache-redis` (Redis or Valkey).
- Docker Compose: an S3-compatible store (SeaweedFS, localhost:58333, buckets `kampus` and `kampus-test`) and Valkey (localhost:56379); CI runs the conformance suites against both.
- `kampus-common`: the error model with problem-details kinds, typed UUIDv7 identifiers, UTC instants with an injectable clock, cursor pagination and request identifiers.
- `kampus-db`: the installation prefix, ordered and checksummed upgrade steps per module, and the upgrade runner that brings any supported release to the current one in one run, serialised across replicas, refusing a database newer than the code or with changed steps.
- `kampus-server`: configuration from a file and `KAMPUS_*` variables validated per role, the commands `serve`, `upgrade` and `check`, liveness and readiness endpoints, request identifiers, problem details, JSON logs and graceful shutdown.
- Container image (`Dockerfile`) and a `server` service in Docker Compose at http://localhost:8100, plus a separate `kampus_test` database for the tests.
- The standard file header with the KAMPUS banner, the licence notice and the author in every file (DEC-083).
- Rust workspace (edition 2024, toolchain 1.100.0) with shared lints that require documentation on every item, and the first crate, `kampus-common`.
- Quality gates in CI: formatting, Clippy with warnings as errors, tests against PostgreSQL 17, `cargo deny` with the licence policy of DEC-085, `cargo audit`, and `tools/repo-check` for file headers, version and changelog, and the dependency rules of the crates.
- Local development with Docker Compose: PostgreSQL 17 and a Rust toolbox image with the same tools as CI.
- The specification of version 0.1.0: requirements, domain models, data models, API fragments, use cases, decisions DEC-001 to DEC-088 and highlights.
- The handbook for every role lives in the private repository `didactika/kampus-docs`, served locally at http://localhost:8096 (DEC-084).
