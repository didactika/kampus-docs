All notable changes to Kampus are recorded here, following [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Versions, support branches and upgrades follow DEC-081 and DEC-082; the **Upgrade** group lists every action an operator must take.

## [Unreleased]

### Changed

- Every component keeps its version data in its own `version.toml`, in the same form as the platform's; `kampus_common::manifest!()` reads it, and no version data is written in code.
- Tests live only in `tests/`, in one folder per kind (`unit`, `integration`, `conformance`, `support`), each one test binary with one file per topic; `tools/repo-check` rejects tests in `src/` and loose test files.
- Code no longer cites the specification: comments, documentation comments and test names describe behaviour in plain words, and `tools/repo-check` rejects identifiers of rules, requirements, use cases, decisions or tasks in code. The explanation of a permission check gives a reason (`allowed`, `no_allow`, `forbidden`, `guest_limit`, `frozen_scope`, `inactive_account`, `view_as_limit`, `unknown_permission`) instead of a rule identifier, and the schema linter reports SQL without a reason as `L-09`.
- Foundation, port, adapter and server crates follow the layout of DEC-087 too: only entry files at the top of `src/`, every concern in a folder with its `mod.rs` (for example `kampus-db`: `connection/`, `schema/`, `upgrade/`, `lint/`; `kampus-server`: `commands/`, `config/`, `http/`, `wiring/`), checked by `tools/repo-check`. Public paths are unchanged, except `kampus_server::run` (now `commands`) and the server's generated registries (now in `wiring/`).
- Every module crate follows one layout (DEC-087): `src/module.rs` exposes the `MODULE` descriptor, and the schema, permissions, model, services, ports, helpers and jobs each live in their folder. The server installs and synchronises modules only from their descriptors, listed in a registry `tools/repo-check --fix` writes from the module crates and from `crates/server/modules.toml`; CI rejects files outside the layout. Paths moved accordingly (for example `kampus_identity::service::sign_in`, `kampus_access::permissions`).
- Crate folders drop the project prefix (`crates/common`, `crates/db`, `crates/server`…), and adapters become sub-plugins of their port in `crates/<port>/adapters/<name>`, registered by URL scheme in a registry `tools/repo-check --fix` writes; external adapters are declared in `crates/server/adapters.toml` (DEC-086).
- The server opens the file storage and the cache from its configuration, through the adapters of the build, and its readiness checks both.
- Kampus is free software under the GNU Affero General Public License, version 3 or later (DEC-085), instead of a proprietary licence.

### Upgrade

- The `worker` and `all` roles now run the jobs of every module and need `KAMPUS_SECURITY_SECRET_KEY`; the `scheduler` and `all` roles fire the schedules. Run at least one of each.
- `kampus_module::http::HttpContext` is now `kampus_module::ServiceContext`, shared by routes and jobs; modules declare `settings`, `events`, `listeners`, `jobs` and `schedules` in their descriptor (empty when they have none), and `PreferenceKind` is now `ValueKind`, shared by preferences and settings.
- The identity policy that was fixed now comes from settings with the same defaults; nothing changes until an operator or an administrator sets a value.
- The `server` and `all` roles now need `KAMPUS_SITE_URL` and `KAMPUS_SECURITY_SECRET_KEY` to serve the API. Until a module delivers mail, the notices of identity (invitations, links, codes) are only logged as due, without their links.
- The configuration file is `config.toml` (was `kampus.toml`), with one table per section; variables follow `KAMPUS_<SECTION>_<KEY>`: `KAMPUS_PUBLIC_URL` is now `KAMPUS_SITE_URL`, `KAMPUS_ROLE` `KAMPUS_SERVER_ROLE`, `KAMPUS_HTTP_ADDRESS` `KAMPUS_SERVER_HTTP_ADDRESS` and `KAMPUS_UPGRADE_ON_START` `KAMPUS_SERVER_UPGRADE_ON_START`. `KAMPUS_SECURITY_SECRET_KEY` (32 bytes in base64) is required by the server and worker roles; `kampus-server install` generates it.
- The first start, or `kampus-server upgrade`, adds the registry of components (`db` step 2) and records every component of the build; from then on every upgrade, downgrade and uninstall is in `kampus-server history`.
- `KAMPUS_STORAGE_URL` is now required for the `server`, `worker` and `all` roles (`file:///path` or `s3://bucket/prefix` with `KAMPUS_STORAGE_S3_ENDPOINT`, `_REGION`, `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY`); `KAMPUS_CACHE_URL` turns on the shared cache.
- New configuration variables: `KAMPUS_HTTP_ADDRESS`, `KAMPUS_CONFIG_FILE`, `KAMPUS_UPGRADE_ON_START`, `KAMPUS_LOG_FORMAT`. A new installation is created by `kampus-server upgrade`, or at start with `KAMPUS_UPGRADE_ON_START=true`.

### Added

- `kampus-settings` (`crates/settings`): modules declare typed settings (`settings` in the descriptor, `src/settings/mod.rs`) with a default, the kinds of scope where each may be set and the permission that sets it; values are kept per scope and resolved from the nearest scope that sets them, unless a scope above locks them, with where the value came from; every change keeps who made it with the value before and after, and publishes `settings.changed` (audited). `kampus-server settings` lists, reads, sets, unsets and shows the history of settings.
- The identity policy of a campus is now made of settings (`identity.self_sign_up`, `identity.password_min_length`, `identity.session_idle_hours` and the others), set for the platform or a campus with the new permission `identity.policy.manage`; `courses.group_mode` is a setting of a course, a section or an activity.
- `kampus-events` (`crates/events`): declared event types with the fields of their payload, published with an outbox entry in the transaction of the change, dispatched after commit into one delivery per listener, delivered at least once and in order per object, retried with a doubling wait and dead after eight attempts, replayable; listeners can be turned off without losing deliveries; chains of events stop after ten; audited types write an append-only audit entry in the same transaction. Modules declare `events` (`src/events/`) and `listeners` (`src/observers/`); the `worker` and `all` roles run the deliveries; `kampus-server events` lists deliveries, replays dead ones, turns listeners on or off and shows the audit log; `events.purge` keeps events 90 days and audit entries two years.
- The first events: `users.system_group_members_changed`, `enrol.enrolment_created`, `enrol.enrolment_updated`, `enrol.enrolment_removed` (audited), `courses.course_created`, `courses.course_state_changed` (audited) and `courses.course_deleted` (audited). Enrolment listens to the members of system groups and brings the instances that follow a group in step at once.
- `kampus-tasks` (`crates/tasks`): a durable job queue on the database. Jobs are enqueued in the transaction that needs them, claimed with `FOR UPDATE SKIP LOCKED` under a lease as long as their timeout, retried with doubling back-off and failed visibly with their error; jobs sharing a concurrency key run one at a time; a job whose worker stops is taken again; long jobs report progress and stop when cancelled. Schedules fire on cron rules read in a time zone, once per instant across every node. Modules declare `jobs` and `schedules` in their descriptor (`src/jobs/`); the `worker` and `all` roles run jobs and the `scheduler` and `all` roles fire schedules. `kampus-server tasks` lists jobs and schedules, retries, cancels, changes a rule and runs a schedule now.
- Scheduled jobs: `identity.purge` (daily) and `identity.run_deletions` (hourly), `enrol.sync` (every 15 minutes) and `enrol.run_expiry` (hourly), `courses.run_deletions` (hourly; a course whose deletion is due goes with everything it owns) and `tasks.purge` (daily).
- `kampus-enrol` (`crates/enrol`): method instances of a course (manual, self, system group) with the role they give, an opening period, capacity, approval and expiry rule; enrolments that own the grant of their role for their period, checked against capacity and period with the instance locked; self-enrolment with keys hashed like passwords, one per course or per group, five wrong keys an hour at most, and requests that wait for a decision; system group instances kept in step with their group; the expiry rule applied once to each ended enrolment. Active participation is computed with the database clock and answers courses through its participants port, so only participants join groups and a course with participants does not go back to draft. Commands `kampus-server enrol sync` and `kampus-server enrol run-expiry`; routes under `/api/v1`.
- `kampus-access`: `grant_for_module_between_in` (a module's grant over a period), `revoke_for_module_in` and `require_may_grant`; `kampus-users`: `member_accounts`.
- `kampus-courses` (`crates/courses`): a tree of categories per campus, courses created as drafts with their first section and owned and taught by their creator, the course lifecycle (published, archived with its scope frozen, deletion scheduled after a grace period and cancelled back to draft), sections nested to any depth, moved with their subtree and deleted recoverably, groups limited to a section or not with manual and module-owned memberships, and group sets. Order among siblings uses fractional sort keys, so a move rewrites only the node that moves; visibility is each node's own and what learners see is computed from the node and its ancestors. Routes under `/api/v1` for categories, courses, sections, groups and group sets, with `If-Match` on every change.
- `kampus-access`: `move_scope_in` (a scope moves with its subtree, grants and overrides), `delete_scope_in`, `set_frozen_in`, `require_while_frozen`, `platform` and `campuses`. A permission declared for the first time, such as one of a module installed on a running site, now reaches the roles that already exist with the value of their template; values an administrator changed stay.
- The HTTP API of identity and users under `/api/v1`: sign-up, confirmation, invitations, sign-in with the second factor, step-up, sign-out, recovery, email change and providers (OIDC start and callback); the account signed in, its password, email, sessions, API tokens, second factors and recovery codes; invitations, service accounts, account transitions and other accounts' tokens for managers; profiles with `ETag` and a required `If-Match`, preferences and system groups. Browsers use the HttpOnly `kampus_session` cookie and send `X-Kampus` with every change; integrations send an API token as `Bearer`, limited to the permissions it carries. Errors are problem details with the request id.
- Modules declare their routes in `src/http/` through `routes` in the descriptor; the server builds the services once, finds the campus of each request and authenticates it before any route (`kampus_module::http`: `HttpContext`, `ApiResult`, `Body`, `id`, `if_match`, `with_etag`).
- `kampus-users` (`crates/users`): profiles (names, language, time zone) saved with `If-Match`, one's own or anyone's with its permission; preferences that modules declare with a type and a default (`preferences` in the descriptor); system groups of a campus or a category whose members are added by hand, by a rule over profiles or by a sync, a rule or a sync removing only what it added.
- Changing the email of an account in `kampus-identity`: step-up, a link to the new address, a notice to the current one, the username following the email when they were equal (`identity` step 2).
- Commands of components: a module declares them in `src/commands/` and the server runs them as `kampus-server <component> <command>`, with `kampus-server <component> --help`; identity offers `purge` and `run-deletions`.
- `kampus-server install`: writes `config.toml`, asking only for what the file and the environment do not give (or nothing with `--non-interactive`), generates the secret key, and creates the installation with its first campus and administrator; an installed database is left as it is. `config.example.toml` shows every section; the image reads `/etc/kampus/config.toml`.
- Multi-tenancy is configured in `[tenancy]` (`single`, or `multi` with a base domain).
- `version.toml` at the root describes the platform release (name, version, maturity, date, `upgrade_from`); the core reads it when it is built, registers the platform as the component `kampus`, and refuses installations older than `upgrade_from`.
- Components with versions (DEC-088): every module, plugin and adapter has a manifest (`kampus_common::manifest!`) built from its `Cargo.toml` and `assets/icon.svg`, with optional maturity, supported Kampus releases and requirements; names follow packages and folders (`kampus-cache-redis` is `cache_redis` in `crates/cache/adapters/redis`); the server checks them all before it installs, upgrades or starts.
- The registry of an installation: the installed version of every component and the ordered history of runs, failed ones included; new versions need an upgrade, and newer or missing components stop the start.
- Data actions in upgrade steps, run once in the step's transaction, and the way back: steps may say how to undo themselves, the SQL is kept when they are applied, and `kampus-server downgrade --yes` undoes newer steps or names the ones it cannot.
- `kampus-server components`, `history`, `downgrade` and `uninstall`; the command line moved to `kampus_server::commands::cli`.
- `kampus-macros`, and Lucide icons for the components of the repository (`THIRD_PARTY.md`).
- `kampus-module` (`crates/module`): the module contract, with the `Module` descriptor and the vocabulary of declarations (scope kinds, values, risks, permissions, role templates).
- Every crate states its kind (`foundation`, `port`, `adapter`, `module`, `server`) in `[package.metadata.kampus]`.
- OpenID Connect providers in `kampus-identity` (RN-028): authorization code flow with PKCE and nonce, the state sealed in the client instead of stored, ID tokens verified against the provider keys; identities link by issuer and subject, by a verified email only when the campus allows it, or after the owner confirms; the sign-in then runs the same pipeline as a password, second factor included.
- Docker Compose and CI start an OpenID provider for the tests (`ghcr.io/navikt/mock-oauth2-server`, localhost:58080).
- Second factors in `kampus-identity`: codes from authenticator apps (RFC 6238, secrets sealed with XChaCha20-Poly1305), codes by email and recovery codes shown once; a sign-in that needs one completes with it, or sets up the first app when the campus or a role requires it; a code is never accepted twice. Access recovery checks the second factor before the new password, is rate-limited, ends every session and token, and never signs in by itself (RN-029, RN-030).
- Roles can require a second factor from the people who hold them (`access` step 2).
- `kampus-identity` (`crates/identity`): accounts of a campus, unique by username and email without regard to case, each the principal of access with its own user scope; sign-up with an email link that never reveals whether an account exists; invitations; the account lifecycle with its history, `If-Match` and one permission per transition; deletion after a grace period that leaves a tombstone; Argon2id passwords checked against the campus policy; hashed, expiring one-time tokens; one sign-in pipeline with throttling per account, per name and per address; server-side sessions revoked at once on suspension or password change, with step-up for sensitive operations; scoped, expiring API tokens; and service accounts that use only tokens. One test per business rule (RN-022 to RN-027, RN-031 to RN-035, RN-039).
- The `unauthenticated` error kind (HTTP 401), for missing or wrong credentials and expired sessions.
- `kampus-access` (`crates/access`): the scope tree with nested sections and its closure table, principals, roles made from versioned templates with their allowances, manual and module-owned grants, overrides, permission checks that explain themselves, "view as", the history of every change, and the default roles of a campus; one test per business rule (RN-001 to RN-021). The server synchronises the declared permissions and templates at start-up.
- The neutral schema of `kampus-db`: modules declare tables, portable types, keys, foreign keys, checks and indexes, and the port writes quoted, prefixed PostgreSQL and indexes every foreign key; upgrade steps are lists of these changes, and SQL outside it needs a reason.
- The schema linter (`kampus_db::lint`), run on every build over every module, and the conformance suite of the database port: every type, reference behaviour, check, error class and `SKIP LOCKED`.
- `kampus_db::classify`, which maps database failures to the error model, and the capabilities of the database port.
- `kampus-storage`: the file storage port (keys, hash-verified writes, ranges, copies, presigned reads as a capability) with its conformance suite, and `kampus-storage-opendal`, which stores on the local disk or in any S3-compatible bucket.
- `kampus-cache`: the cache port (entries with a time to live, counters with a window, locks with a lease) with its conformance suite and the two-level `Layered` cache, and its adapters `kampus-cache-moka` (in-process) and `kampus-cache-redis` (Redis or Valkey).
- Docker Compose: an S3-compatible store (SeaweedFS, localhost:58333, buckets `kampus` and `kampus-test`) and Valkey (localhost:56379); CI runs the conformance suites against both.
- `kampus-common`: the error model with problem-details kinds, typed UUIDv7 identifiers, UTC instants with an injectable clock, cursor pagination and request identifiers.
- `kampus-db`: the installation prefix, ordered and checksummed upgrade steps per module, and the upgrade runner that brings any supported release to the current one in one run, serialised across replicas, refusing a database newer than the code or with changed steps.
- `kampus-server`: configuration from a file and `KAMPUS_*` variables validated per role, the commands `serve`, `upgrade` and `check`, liveness and readiness endpoints, request identifiers, problem details, JSON logs and graceful shutdown.
- Container image (`Dockerfile`) and a `server` service in Docker Compose at http://localhost:8100, plus a separate `kampus_test` database for the tests.
- The standard file header with the KAMPUS banner, the licence notice and the author in every file (DEC-083).
- Rust workspace (edition 2024, toolchain 1.100.0) with shared lints that require documentation on every item, and the first crate, `kampus-common`.
- Quality gates in CI: formatting, Clippy with warnings as errors, tests against PostgreSQL 17, `cargo deny` with the licence policy of DEC-085, `cargo audit`, and `tools/repo-check` for file headers, version and changelog, and the dependency rules of the crates.
- Local development with Docker Compose: PostgreSQL 17 and a Rust toolbox image with the same tools as CI.
- The specification of version 0.1.0: requirements, domain models, data models, API fragments, use cases, decisions DEC-001 to DEC-088 and highlights.
- The handbook for every role lives in the private repository `didactika/kampus-docs`, served locally at http://localhost:8096 (DEC-084).
